# 日程助理、对话状态与人工接管 TODO（2026-09-12）

## 1. 目标

将当前“最近消息 + 当前问题”的无状态 LLM 调用，演进为一个平时作为日程助理运行、可持久化、可恢复、支持人工介入的对话工作流，同时保留普通问答的轻量路径。

首批新增能力：

- 默认以日程助理身份运行：帮助用户记录、查询、整理和跟进日程安排，而不是每轮都作为泛化客服回答。
- Admin 页面提供明确的人工接管按钮；接管后默认只生成回复建议，不向用户自动发送，恢复自动模式需要显式操作。
- 个人中心支持查看行程安排卡片，展示时间、标题、地点、参与人、状态、备注和来源，并与原始消息或文档关联。
- 设置一段稳定的欢迎语，让用户知道客服可以提供的服务、当前工作模式和可用指令关键词。
- 支持更多业务意图，并允许每种意图进入独立工作流。
- 自动识别需要整理的信息，进入内部信息捕获工作流：默认持续到最后一条新消息后的 10 分钟，将期间收到的信息整理为一个或多个 Markdown 文档，并提取结构化待办；用户不必学习或显式切换内部模式。
- Admin 支持账号级默认回复策略，以及单会话人工接管/恢复自动回复。
- 人工接管时模型只生成回复建议，不直接向客户发送；人工可编辑、发送或忽略建议。
- 改善上下文构建和可观测性，避免仅依赖滚动截取最近 12 条消息。

## 2. 设计原则

- 消息流水是不可变事实来源；工作流状态、摘要、文档和待办均可由消息追溯。
- 回复策略、活动工作流和工作流阶段相互独立，避免用一个状态字段表达所有组合。
- 意图只负责路由到工作流；进入工作流后由确定性状态迁移决定下一步，不在每轮重新猜测意图。
- 用户不需要理解内部工作流名称；意图置信度不足时先提出有限选项进行澄清，而不是擅自创建日程或文档。
- 所有状态和定时截止时间持久化，进程重启后可以恢复。
- LLM 不直接执行不可逆操作；发消息和其他外部副作用必须经过策略门、幂等键和发送前复核。
- 日程时间统一保存为 UTC，同时保留用户时区；展示、提醒和日期解析必须明确时区。
- 欢迎语和指令关键词优先走确定性路由，不能依赖 LLM 猜测后才决定是否执行系统命令。
- SQLite/后续正式数据库保存业务事实；LangGraph 只负责编排，不作为消息已发送或业务已完成的唯一依据。

## 3. 正交状态模型

### 3.1 回复策略

```text
reply_mode
  auto          自动生成并发送
  suggest_only  只生成建议，人工确认后发送
  human_only    完全人工，不调用 LLM 生成回复
```

- 账号级配置决定新会话的默认策略。
- 会话级配置可以覆盖账号默认值，并记录操作员和修改时间。
- `suggest_only` 与信息捕获等工作流可以同时存在：模型继续整理信息和生成建议，但不得自动发送。
- 策略从 `auto` 切换后，已经在运行的任务也必须在发送前重新读取策略；不得依赖任务启动时的旧值。

### 3.2 工作流与阶段

```text
workflow_type
  schedule_assistant
  information_capture
  order_query
  refund
  ...

workflow_status
  active
  completed
  cancelled
  expired

phase
  collecting
  reviewing
  confirming
  executing
  finalizing
```

- 同一会话首期只允许一个活动工作流，后续确有并行任务需求时再扩展。
- 普通问答不强制创建工作流实例。
- 日程助理作为默认工作流入口，但简单闲聊和知识问答仍可走轻量路径。
- 每个工作流定义允许的状态迁移、槽位 schema、超时策略和完成条件。

### 3.3 日程助理模式

```text
assistant_mode
  schedule_assistant   默认日程助理
  information_capture  自动识别的信息捕获（内部工作流）
  human_handoff        人工接管中
```

- 日程助理负责识别“记录、查询、修改、取消、提醒、整理”类日程意图。
- “人工接管”是回复策略和界面控制，不应覆盖或删除日程数据；人工可以继续查看和编辑用户日程。
- 日程意图不明确时先追问缺失信息，不得擅自创建含糊或错误的行程。

## 4. 自动识别的信息捕获工作流

### 4.1 生命周期

```text
识别出用户正在连续提供需要整理的信息
  -> collecting
  -> 持续接收并关联原始消息
  -> 增量提取主题、事实、决定、待办和待确认项
  -> 每条有效新消息将 expires_at 顺延 10 分钟
  -> 用户显式结束或到期
  -> finalizing
  -> 生成 Markdown artifact 与结构化待办
  -> completed
```

- “10 分钟”定义为无新消息 10 分钟，而不是从第一条消息开始的固定窗口。
- 用户不需要显式进入该工作流；系统可根据连续消息、整理意图和上下文信号自动进入。
- 支持“结束整理”“延长 10 分钟”“取消整理”等显式控制命令，作为可靠的收尾和中止入口。
- 当意图置信度不足时先询问用户是要记录日程、查询安排、整理信息还是转人工；不得直接创建工作流或日程。
- 超时采用持久化 `expires_at`；启动恢复及周期扫描均可推进过期实例，不能依赖单进程内存定时器。
- 到期与新消息并发时使用状态版本或事务条件更新，避免一边完成、一边继续写入。
- 原始消息始终保存；增量提取失败不得丢失消息，可安全重试。

### 4.2 欢迎语与指令关键词

欢迎语应作为稳定的系统/业务配置，在新会话首条回复或用户主动询问帮助时使用，至少说明：

- 这是日程助理，能记录、查询、修改、取消和整理行程。
- 可以连续发送资料，系统会自动判断是否需要整理为文档和待办。
- 如已支持人工接管，可简要介绍人工协助能力，无需罗列触发说法。
- 发送“个人中心”可获取一次性登录链接，进入后查看自己的记录和已上线的行程安排卡片。

#### 企业微信可直接配置的欢迎语

以下为日程与整理能力上线后的欢迎语，可直接粘贴到企业微信客服配置中；上线前按实际可用能力调整介绍：

```text
你好，我是你的个人助理，可以帮你管理日程、整理资料和记录待办。有什么需要，直接告诉我就好，也可以连续发送信息。

发送“个人中心”，即可获取一次性登录链接，查看自己的记录和日程。
```

如果企业微信配置框对字数有限制，可使用以下短版：

```text
你好，我是你的个人助理，帮你管理日程、整理资料和记录待办，直接告诉我需求就好。发送“个人中心”获取一次性登录链接，查看自己的记录和日程。
```

配置要求：

- 欢迎语应与系统中的 `welcome_message` 保持一致，修改时同步更新版本和审计记录。
- 欢迎语只介绍用户可使用的能力，不把内部工作流名称（如 `information_capture`）展示给用户。
- 欢迎语只展示需要字符串匹配的个人中心登录指令；日程、整理等由模型理解的需求用能力介绍表达，不罗列“新增日程”等关键词或要求用户记忆固定说法。
- 个人中心登录继续复用现有一次性票据流程，包括有效期、单次消费、生成限流和历史中的链接隐藏；票据有效期调整时同步更新欢迎语。

必须保留现有个人中心登录关键词及别名，走确定性字符串匹配，不依赖 LLM 判断或生成登录链接；欢迎语只展示“个人中心”这一主入口：

```text
个人中心 / 我的信息 / 我的消息 / 查看记录
```

以下为内部命令路由候选及别名，不要求展示在欢迎语中；确定性命令与模型理解的自然语言需求应分开处理：

```text
帮助 / 菜单 / 你能做什么
我的日程 / 行程 / 安排
新增日程 / 记录日程 / 预约
修改日程 / 改一下安排
取消日程 / 删除安排
整理这些信息 / 开始整理 / 结束整理
转人工 / 人工客服 / 停止自动回复
恢复自动 / 继续自动回复
```

- 关键词匹配应支持大小写、空白和常见中文标点归一化，但不能误把长句中的普通提及当作命令。
- “开始整理”属于可选的高级快捷指令，不是普通用户必须执行的模式切换；自然语言整理需求应由意图路由自动识别。
- 指令执行结果要落入统一消息流水，并在需要时创建或更新工作流状态。
- 欢迎语、服务说明和关键词列表应可配置但有安全默认值；修改需记录操作员和版本。

### 4.3 结构化中间状态

```json
{
  "topics": [],
  "facts": [],
  "decisions": [],
  "todos": [
    {
      "title": "",
      "owner": null,
      "due_at": null,
      "status": "pending",
      "source_message_ids": []
    }
  ],
  "open_questions": []
}
```

- 每个事实、决定和待办尽可能保留来源消息 ID，方便 Admin 回溯。
- 待办应作为独立结构化记录保存，而不是只存在于 Markdown 正文中。
- 最终文档根据主题决定生成单个或多个 Markdown；拆分规则必须稳定且可测试。
- Artifact 支持版本号、生成状态和重新生成，不覆盖人工修改的版本。

## 5. 建议数据模型

### 5.1 工作流实例

```text
workflow_instance
  id
  conversation_id
  workflow_type
  status
  phase
  state_json
  expires_at nullable
  state_version
  created_at
  updated_at
  completed_at nullable
```

约束：同一会话最多一个 `status = active` 的实例；状态更新使用 `state_version` 做乐观并发控制。

### 5.2 工作流消息关联

```text
workflow_message
  workflow_id
  conversation_message_id
  consumed_at
  PRIMARY KEY(workflow_id, conversation_message_id)
```

用于确保回调重放、任务重试和恢复扫描不会重复消费同一消息。

### 5.3 文档与待办

```text
artifact
  id
  workflow_id
  title
  slug
  content_markdown
  version
  generation_status
  is_manually_edited
  created_at
  updated_at

todo_item
  id
  workflow_id
  artifact_id nullable
  title
  owner nullable
  due_at nullable
  status
  source_message_ids_json
  created_at
  updated_at
```

### 5.4 日程安排与个人中心卡片

```text
schedule_item
  id
  user_id
  conversation_id
  title
  description
  starts_at_utc
  ends_at_utc nullable
  timezone
  location nullable
  participants_json
  status              planned / completed / cancelled
  reminder_at_utc nullable
  source_message_ids_json
  source_workflow_id nullable
  created_at
  updated_at
```

- 日程卡片只展示当前用户有权查看的安排，不向个人中心暴露客服内部备注、外部用户 ID 或操作员信息。
- 个人中心按用户时区展示日期和时间，支持“即将开始、今天、未来、已完成、已取消”等分组。
- 卡片至少支持标题、时间、地点、参与人、状态和备注；可跳转到关联会话或信息捕获文档的安全摘要。
- 首期只读展示；日程修改和取消由聊天指令或 Admin 完成，后续再评估个人中心直接编辑。
- 创建、修改、取消必须保留来源消息和状态变更记录，避免模型重复创建同一日程。

### 5.5 回复策略、欢迎语与建议

```text
account_settings
  open_kfid
  default_reply_mode
  welcome_message
  service_description
  command_keywords_json
  updated_by
  updated_at

conversation_control
  conversation_id
  reply_mode nullable
  updated_by
  updated_at

reply_suggestion
  id
  conversation_id
  based_on_message_id
  based_on_state_version
  content
  status
  created_at
  reviewed_at nullable
  reviewed_by nullable
  sent_message_id nullable
```

建议状态至少包括 `pending / stale / sent / dismissed / failed`。同一消息和状态版本的建议生成应有唯一约束或稳定幂等键。

### 5.6 定时动作

```text
scheduled_action
  id
  conversation_id
  workflow_id nullable
  schedule_item_id nullable
  action_type          reminder / follow_up / finalize_workflow
  due_at_utc
  payload_json
  status               pending / processing / sent / blocked / failed / cancelled
  idempotency_key
  attempts
  lease_until nullable
  created_at
  updated_at
```

- Scheduler 只负责领取到期动作；LangGraph 或工作流执行器负责决定到期后做什么。
- 任务执行时重新读取人工接管状态、最新消息、日程状态和企业微信回复额度，不能使用创建任务时的旧判断。
- 用户新消息、日程取消、工作流完成或管理员接管都可以取消未执行动作。
- `due_at_utc`、租约和幂等键必须持久化；服务重启或多 worker 扫描不能导致重复提醒。
- 若当前不允许自动发送，动作转为 `blocked` 或生成 Admin 建议，不应无限重试。

## 6. 消息处理图

```text
ingest
  -> deduplicate
  -> load conversation control and active workflow
  -> route
       -> normal QA
       -> schedule assistant
       -> information capture (internal workflow)
       -> other business workflow
       -> human-only path
  -> persist state/artifacts/todos
  -> generate answer or suggestion
  -> policy gate (重新读取最新策略与状态)
       -> auto: send with idempotency
       -> suggest_only: save suggestion
       -> human_only: do not call/send through LLM
```

- 企业微信 cursor 推进、客户级锁、回复额度和消息发送幂等继续由现有业务层保证。
- 日程创建、修改、取消和提醒必须经过确定性命令/工具节点及幂等校验，LLM 只能提出结构化参数。
- 日程提醒由 Scheduler 触发，再进入策略门；Scheduler 不直接绕过人工接管或企业微信限制发送。
- 建议生成失败不影响客户消息入库和工作流继续收集。
- 人工发送建议时继续复用现有 48 小时窗口、五次额度和发送失败重试逻辑。

## 7. 上下文与缓存策略

- 新增独立 `ContextBuilder`，禁止业务处理器直接拼接任意消息数组。
- Prompt 按以下顺序构建：稳定系统规则、稳定业务规则/知识、结构化活动状态、未解决事项、少量近期原文、当前批次。
- 增加会话空闲结束或显式重置规则，避免一个客户在同一客服账号下永久共享同一语义上下文。
- 不再仅依赖固定“最近 12 条”；关键事实进入结构化状态或摘要，近期原文只负责语言和局部指代。
- 记录供应商返回的 input tokens、output tokens、cached tokens、模型、延迟和失败类型，不记录消息全文或敏感标识。
- 先用指标验证缓存收益；LangGraph 本身不负责提高 prompt cache 命中率。

## 8. Admin 界面

- [ ] 在会话头部新增醒目的“人工接管 / 恢复自动回复”按钮，显示当前策略、操作者和最后更新时间；接管后立即阻止在途任务自动发送。
- [ ] 新增账号级默认回复策略开关；默认运行日程助理，开启人工接管时默认使用 `suggest_only`，而不是完全禁用模型。
- [ ] 单会话支持 `自动回复 / 回复建议 / 完全人工` 三态切换，并明确显示账号默认值和会话覆盖值。
- [ ] 提供欢迎语、服务说明和指令关键词的管理入口，预览发送给用户的实际内容并保留版本/审计记录。
- [ ] 展示当前活动工作流、阶段、剩余收集时间，以及结束、延长、取消操作。
- [ ] 展示当前用户的近期日程、待确认日程和待发送提醒，并支持进入对应会话。
- [ ] 建议卡片支持编辑、发送、忽略和重新生成。
- [ ] 收到更新的客户消息或工作流状态变化后，将旧建议实时标记为“已过期”，发送按钮不可用。
- [ ] 展示生成的 Markdown 文档，支持预览、复制、下载和查看版本。
- [ ] 展示结构化待办，支持编辑负责人、截止时间和完成状态，并能回溯来源消息。
- [ ] 所有策略切换、人工发送、建议处置和文档人工编辑记录操作员审计信息。

## 9. LangGraph 引入边界

- [ ] 第一阶段先定义框架无关的 `ConversationState`、工作流接口、节点输入输出和状态迁移测试。
- [ ] 使用自动识别的信息捕获工作流验证暂停、超时恢复、人工介入和 artifact 生成；用户不需要显式进入内部模式。
- [ ] 使用“日程助理”工作流验证结构化槽位、日程增改取消、提醒动作和人工接管。
- [ ] 当至少存在多个有分支、工具调用、确认/暂停需求的工作流时，再将编排层接入 LangGraph。
- [ ] LangGraph checkpoint 复用现有数据库或明确独立存储策略，并定义与业务事务的边界。
- [ ] 节点必须可重入；外部副作用节点需要业务幂等键，checkpoint 成功不等于外部发送成功。
- [ ] 保留不经过图的普通问答快速路径，避免简单咨询承担不必要的编排成本。

## 11. 验收标准

- [ ] 开启账号级人工接管后，新客户消息不会由任何在途自动任务直接发送回复，只会产生有效建议。
- [ ] Admin 点击“人工接管”后，正在等待发送的自动回复和提醒均在发送前被拦截；恢复自动回复后才可继续。
- [ ] 单会话覆盖策略生效，移除覆盖后恢复账号默认值。
- [ ] 新会话首条欢迎语简要介绍已上线的个人助理能力，并明确发送“个人中心”可获取一次性登录链接，不罗列由模型理解的业务关键词。
- [ ] “个人中心 / 我的信息 / 我的消息 / 查看记录”继续通过确定性路由获取一次性登录链接，原有有效期、单次消费、限流及历史链接隐藏行为保持有效。
- [ ] 关键词命令可稳定触发帮助、日程查询、整理收尾、取消和人工接管，不依赖模型自由发挥；普通整理需求可由意图路由自动识别。
- [ ] 建议生成后若客户又发消息，旧建议必定变为 `stale` 且不能发送。
- [ ] 日程创建、修改和取消不会因重复回调或模型重试而重复执行；每条日程可追溯到来源消息。
- [ ] 个人中心只显示当前用户有权查看的行程卡片，时间按用户时区正确展示。
- [ ] 到期提醒在自动模式下遵守人工接管、企业微信回复窗口和次数限制；不满足时转为阻塞或建议。
- [ ] 自动识别的信息捕获工作流每次收到新消息都将到期时间顺延 10 分钟；重启后仍能按持久化时间正确完成。
- [ ] 重复回调和任务重试不会重复消费消息、创建重复待办、重复生成同版本文档或重复发送。
- [ ] 到期和新消息并发时只产生一种合法结果，不丢消息。
- [ ] 最终 Markdown 覆盖本次工作流的全部有效消息；每个待办能追溯来源，并可独立维护状态。
- [ ] 自动、建议和完全人工三种模式均遵守企业微信回复窗口、次数限制和现有幂等规则。
- [ ] 普通问答延迟没有因引入工作流框架明显退化。
- [ ] 指标可比较改造前后的平均输入 token、cached token 比例、成本和端到端延迟。

## 12. 暂不纳入首期

- 多个活动工作流并行运行及工作流间依赖。
- 多人实时协同编辑 Markdown。
- 自动执行待办、自动调用不可逆外部业务操作；首期提醒只发送通知，不自动完成外部业务动作。
- 复杂坐席排班、队列分配和完整 RBAC。
- 用向量检索替代结构化工作流状态。
