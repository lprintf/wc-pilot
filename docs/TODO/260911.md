# 对话状态、信息处理与人工接管 TODO（2026-09-11）

## 1. 目标

将当前“最近消息 + 当前问题”的无状态 LLM 调用，演进为可持久化、可恢复、支持人工介入的对话工作流，同时保留普通问答的轻量路径。

首批新增能力：

- 支持更多业务意图，并允许每种意图进入独立工作流。
- 支持“信息处理”模式：默认持续到最后一条新消息后的 10 分钟，将期间收到的信息整理为一个或多个 Markdown 文档，并提取结构化待办。
- Admin 支持账号级“默认人工接管”开关，以及单会话回复策略覆盖。
- 人工接管时模型只生成回复建议，不直接向客户发送；人工可编辑、发送或忽略建议。
- 改善上下文构建和可观测性，避免仅依赖滚动截取最近 12 条消息。

## 2. 设计原则

- 消息流水是不可变事实来源；工作流状态、摘要、文档和待办均可由消息追溯。
- 回复策略、活动工作流和工作流阶段相互独立，避免用一个状态字段表达所有组合。
- 意图只负责路由到工作流；进入工作流后由确定性状态迁移决定下一步，不在每轮重新猜测意图。
- 所有状态和定时截止时间持久化，进程重启后可以恢复。
- LLM 不直接执行不可逆操作；发消息和其他外部副作用必须经过策略门、幂等键和发送前复核。
- SQLite/后续正式数据库保存业务事实；LangGraph 只负责编排，不作为消息已发送或业务已完成的唯一依据。

## 3. 正交状态模型

### 3.1 回复策略

```text
reply_mode
  auto          自动生成并发送
  suggest_only  只生成建议，人工确认后发送
  human_only    完全人工，不调用 LLM 生成回复
```

- 账号级配置决定新会话的默认策略。
- 会话级配置可以覆盖账号默认值，并记录操作员和修改时间。
- `suggest_only` 与“信息处理”等工作流可以同时存在：模型继续整理信息和生成建议，但不得自动发送。
- 策略从 `auto` 切换后，已经在运行的任务也必须在发送前重新读取策略；不得依赖任务启动时的旧值。

### 3.2 工作流与阶段

```text
workflow_type
  information_capture
  order_query
  refund
  ...

workflow_status
  active
  completed
  cancelled
  expired

phase
  collecting
  reviewing
  confirming
  executing
  finalizing
```

- 同一会话首期只允许一个活动工作流，后续确有并行任务需求时再扩展。
- 普通问答不强制创建工作流实例。
- 每个工作流定义允许的状态迁移、槽位 schema、超时策略和完成条件。

## 4. “信息处理”工作流

### 4.1 生命周期

```text
识别或显式进入信息处理
  -> collecting
  -> 持续接收并关联原始消息
  -> 增量提取主题、事实、决定、待办和待确认项
  -> 每条有效新消息将 expires_at 顺延 10 分钟
  -> 用户显式结束或到期
  -> finalizing
  -> 生成 Markdown artifact 与结构化待办
  -> completed
```

- “10 分钟”定义为无新消息 10 分钟，而不是从第一条消息开始的固定窗口。
- 支持“结束整理”“延长 10 分钟”“取消整理”等显式命令。
- 超时采用持久化 `expires_at`；启动恢复及周期扫描均可推进过期实例，不能依赖单进程内存定时器。
- 到期与新消息并发时使用状态版本或事务条件更新，避免一边完成、一边继续写入。
- 原始消息始终保存；增量提取失败不得丢失消息，可安全重试。

### 4.2 结构化中间状态

```json
{
  "topics": [],
  "facts": [],
  "decisions": [],
  "todos": [
    {
      "title": "",
      "owner": null,
      "due_at": null,
      "status": "pending",
      "source_message_ids": []
    }
  ],
  "open_questions": []
}
```

- 每个事实、决定和待办尽可能保留来源消息 ID，方便 Admin 回溯。
- 待办应作为独立结构化记录保存，而不是只存在于 Markdown 正文中。
- 最终文档根据主题决定生成单个或多个 Markdown；拆分规则必须稳定且可测试。
- Artifact 支持版本号、生成状态和重新生成，不覆盖人工修改的版本。

## 5. 建议数据模型

### 5.1 工作流实例

```text
workflow_instance
  id
  conversation_id
  workflow_type
  status
  phase
  state_json
  expires_at nullable
  state_version
  created_at
  updated_at
  completed_at nullable
```

约束：同一会话最多一个 `status = active` 的实例；状态更新使用 `state_version` 做乐观并发控制。

### 5.2 工作流消息关联

```text
workflow_message
  workflow_id
  conversation_message_id
  consumed_at
  PRIMARY KEY(workflow_id, conversation_message_id)
```

用于确保回调重放、任务重试和恢复扫描不会重复消费同一消息。

### 5.3 文档与待办

```text
artifact
  id
  workflow_id
  title
  slug
  content_markdown
  version
  generation_status
  is_manually_edited
  created_at
  updated_at

todo_item
  id
  workflow_id
  artifact_id nullable
  title
  owner nullable
  due_at nullable
  status
  source_message_ids_json
  created_at
  updated_at
```

### 5.4 回复策略与建议

```text
account_settings
  open_kfid
  default_reply_mode
  updated_by
  updated_at

conversation_control
  conversation_id
  reply_mode nullable
  updated_by
  updated_at

reply_suggestion
  id
  conversation_id
  based_on_message_id
  based_on_state_version
  content
  status
  created_at
  reviewed_at nullable
  reviewed_by nullable
  sent_message_id nullable
```

建议状态至少包括 `pending / stale / sent / dismissed / failed`。同一消息和状态版本的建议生成应有唯一约束或稳定幂等键。

## 6. 消息处理图

```text
ingest
  -> deduplicate
  -> load conversation control and active workflow
  -> route
       -> normal QA
       -> information capture
       -> other business workflow
       -> human-only path
  -> persist state/artifacts/todos
  -> generate answer or suggestion
  -> policy gate (重新读取最新策略与状态)
       -> auto: send with idempotency
       -> suggest_only: save suggestion
       -> human_only: do not call/send through LLM
```

- 企业微信 cursor 推进、客户级锁、回复额度和消息发送幂等继续由现有业务层保证。
- 建议生成失败不影响客户消息入库和工作流继续收集。
- 人工发送建议时继续复用现有 48 小时窗口、五次额度和发送失败重试逻辑。

## 7. 上下文与缓存策略

- 新增独立 `ContextBuilder`，禁止业务处理器直接拼接任意消息数组。
- Prompt 按以下顺序构建：稳定系统规则、稳定业务规则/知识、结构化活动状态、未解决事项、少量近期原文、当前批次。
- 增加会话空闲结束或显式重置规则，避免一个客户在同一客服账号下永久共享同一语义上下文。
- 不再仅依赖固定“最近 12 条”；关键事实进入结构化状态或摘要，近期原文只负责语言和局部指代。
- 记录供应商返回的 input tokens、output tokens、cached tokens、模型、延迟和失败类型，不记录消息全文或敏感标识。
- 先用指标验证缓存收益；LangGraph 本身不负责提高 prompt cache 命中率。

## 8. Admin 界面

- [ ] 新增账号级“默认人工接管”开关；开启时默认使用 `suggest_only`，而不是完全禁用模型。
- [ ] 单会话支持 `自动回复 / 回复建议 / 完全人工` 三态切换，并明确显示账号默认值和会话覆盖值。
- [ ] 展示当前活动工作流、阶段、剩余收集时间，以及结束、延长、取消操作。
- [ ] 建议卡片支持编辑、发送、忽略和重新生成。
- [ ] 收到更新的客户消息或工作流状态变化后，将旧建议实时标记为“已过期”，发送按钮不可用。
- [ ] 展示生成的 Markdown 文档，支持预览、复制、下载和查看版本。
- [ ] 展示结构化待办，支持编辑负责人、截止时间和完成状态，并能回溯来源消息。
- [ ] 所有策略切换、人工发送、建议处置和文档人工编辑记录操作员审计信息。

## 9. LangGraph 引入边界

- [ ] 第一阶段先定义框架无关的 `ConversationState`、工作流接口、节点输入输出和状态迁移测试。
- [ ] 使用一个“信息处理”工作流验证暂停、超时恢复、人工介入和 artifact 生成。
- [ ] 当至少存在多个有分支、工具调用、确认/暂停需求的工作流时，再将编排层接入 LangGraph。
- [ ] LangGraph checkpoint 复用现有数据库或明确独立存储策略，并定义与业务事务的边界。
- [ ] 节点必须可重入；外部副作用节点需要业务幂等键，checkpoint 成功不等于外部发送成功。
- [ ] 保留不经过图的普通问答快速路径，避免简单咨询承担不必要的编排成本。

## 11. 验收标准

- [ ] 开启账号级人工接管后，新客户消息不会由任何在途自动任务直接发送回复，只会产生有效建议。
- [ ] 单会话覆盖策略生效，移除覆盖后恢复账号默认值。
- [ ] 建议生成后若客户又发消息，旧建议必定变为 `stale` 且不能发送。
- [ ] “信息处理”每次收到新消息都将到期时间顺延 10 分钟；重启后仍能按持久化时间正确完成。
- [ ] 重复回调和任务重试不会重复消费消息、创建重复待办、重复生成同版本文档或重复发送。
- [ ] 到期和新消息并发时只产生一种合法结果，不丢消息。
- [ ] 最终 Markdown 覆盖本次工作流的全部有效消息；每个待办能追溯来源，并可独立维护状态。
- [ ] 自动、建议和完全人工三种模式均遵守企业微信回复窗口、次数限制和现有幂等规则。
- [ ] 普通问答延迟没有因引入工作流框架明显退化。
- [ ] 指标可比较改造前后的平均输入 token、cached token 比例、成本和端到端延迟。

## 12. 暂不纳入首期

- 多个活动工作流并行运行及工作流间依赖。
- 多人实时协同编辑 Markdown。
- 自动执行待办、自动调用不可逆外部业务操作。
- 复杂坐席排班、队列分配和完整 RBAC。
- 用向量检索替代结构化工作流状态。
