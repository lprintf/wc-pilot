# 面向普通微信用户的 AI 客服展示助手 TODO（2026-09-16）

## 1. 目标与范围

停止继续演进“日程助理”方向，复用当前已跑通的微信客服 PoC，将系统调整为面向普通微信用户的“个人助理客服”展示 Demo。

当前已经具备并可继续复用的能力：

- 普通微信用户通过微信客服进入会话并收到回复的事件回调链路。
- `kf/sync_msg`、`kf/send_msg`、`cursor` 持久化、消息幂等。
- SQLite 用户、身份、客户资料、会话和消息存储。
- LLM 非流式问答、失败兜底、回复配额与 48 小时窗口提示。
- Admin 客服后台、人工发送、客户管理和个人中心 H5。

本次改造后，系统目标是：

- 以微信客服为入口，面向所有普通微信用户提供展示型 AI 客服。
- 可检索 Markdown 知识库，回答用户问题，并给出可追溯的知识来源。
- 向潜在客户介绍我们能帮助实现的客服场景，例如获客引流客服、售后客服。
- 能与用户多轮深入沟通业务场景，分析成本与技术可行性，识别可落地的 AI 应用点。
- 保留人工接管和既有消息链路，不破坏当前微信端验证结果。

## 2. 设计原则

- 微信客服消息链路保持现状；本次重点是在现有 `sync_msg -> LLM -> send_msg` 中插入 LangGraph 编排层，不重写微信 API 层。
- LangGraph 只负责对话编排、意图路由、知识检索和流程状态；SQLite 继续作为业务事实与持久化状态的唯一来源。
- 最终发消息仍必须经过现有 `send_reply` 的配额、幂等和发送前校验，不能由 LangGraph 绕过。
- 知识库以 Markdown 文件为源，检索结果必须可追溯；找不到依据时明确说明，不编造。
- 展示能力时区分“已实现能力”和“可交付方案”，不承诺未验证指标，不泄露系统提示词、密钥或客户数据。
- 微信客服每个 48 小时窗口只有 5 条回复额度，多轮咨询必须合并提问、引导批量回答，并把额度变化反馈给用户。
- 先交付可演示闭环，再优化语义检索、成本模型和后台配置。

## 3. 对话定位与人设

系统身份调整为"AI 客服展示助手"，不冒充真人客服。首条欢迎语应简要说明：

- 本客服能演示什么：知识库问答、获客引流客服、售后客服、业务咨询。
- 用户如何参与：直接描述业务场景，系统会追问行业、渠道、咨询量和痛点。
- 用户发送"个人中心""查看记录"等关键词可获取一次性登录链接，查看客服历史。
- 当前是 Demo，回复次数和有效期受微信客服规则限制。

默认回复语言为简体中文，语气简洁、专业、可行动，并适配微信文本长度。现有“剩余回复次数”footer 继续保留，但在展示型回复中避免过度抢戏。

## 4. 意图路由

首期支持以下意图，后续可按知识库扩展：

```text
greeting
capabilities
knowledge_qa
lead_gen
after_sales
business_discovery
cost_feasibility
human_handoff
other
```

- `greeting`：发送欢迎语和能力菜单，引导用户说出业务场景。
- `capabilities`：介绍获客引流客服、售后客服、知识库问答、人工协同等能力。
- `knowledge_qa`：检索 Markdown 知识库，基于片段回答问题并附来源。
- `lead_gen`：进入获客引流场景，收集行业、获客渠道、线索分发方式和转化目标。
- `after_sales`：进入售后场景，收集工单量、常见问题、SLA 和系统对接需求。
- `business_discovery`：多轮收集业务事实，每轮合并提问，减少微信回复额度消耗。
- `cost_feasibility`：根据已收集信息和知识库成本模型，给出阶段估算与技术可行性。
- `human_handoff`：表达需要人工、商务或进一步演示时，给出明确 CTA，并在 Admin 后台标记可跟进状态。
- `other`：不强行进入业务流程；先澄清问题，必要时转人工或提示换种问法。

意图识别采用“系统命令确定性路由，业务意图交给 LLM”的策略；仅 profile 命令（个人中心、我的信息、我的消息、查看记录）硬编码，其他意图交给 LangGraph/LLM 分类。

## 5. LangGraph 编排设计

### 5.1 节点

```text
load_conversation
detect_intent
route_intent
retrieve_knowledge
answer_with_kb
describe_capabilities
discover_business_scenario
estimate_cost_feasibility
escalate_to_human
finalize_reply
persist_state
```

节点职责：

- `load_conversation`：加载用户、会话、历史消息和上次流程状态。
- `detect_intent`：结合当前批消息、历史上下文和知识库关键词识别意图。
- `route_intent`：根据意图选择后续节点。
- `retrieve_knowledge`：查询知识库索引，返回 top 片段及来源。
- `answer_with_kb`：基于知识片段生成回答，缺失信息时明确说明并给出追问。
- `describe_capabilities`：根据能力知识库介绍获客、售后、知识问答等场景。
- `discover_business_scenario`：按步骤追问并记录行业、渠道、量级、痛点、目标和现有系统。
- `estimate_cost_feasibility`：生成成本区间、技术可行性、风险、分阶段落地建议和下一步。
- `escalate_to_human`：生成转人工/商务 CTA，并记录会话状态。
- `finalize_reply`：截断、追加 footer、检查敏感内容、确保不超过微信文本限制。
- `persist_state`：持久化意图、流程步骤、业务事实和成本分析结果。

### 5.2 状态模型

```text
CustomerServiceState
  user_id
  conversation_id
  open_kfid
  external_userid
  incoming_messages
  intent
  knowledge_chunks
  discovery_step
  business_facts
  estimate
  reply_text
  error
```

LangGraph 使用 SQLite checkpoint 持久化，thread id 使用内部 `user_id` 或 `conversation_id`。服务重启后应从 checkpoint 恢复，不依赖内存状态，也不能重复消费同一批消息。

## 6. Markdown 知识库与检索

### 6.1 文件与目录

建议目录：

```text
backend/knowledge/
  capabilities.md
  scenarios.md
  pricing.md
  implementation.md
  faq.md
```

首期 Demo 知识库至少包含：

- `capabilities.md`：获客引流客服、售后客服、知识库问答、人工协同等能力边界。
- `scenarios.md`：典型行业、业务场景、痛点和落地示例。
- `pricing.md`：成本估算公式、主要成本项、量级分档和 Demo 说明。
- `implementation.md`：PoC、试点、生产化三阶段，技术依赖和交付周期。
- `faq.md`：常见问题、系统能力、微信客服规则说明。

每个 Markdown 文件使用稳定标题层级作为切分依据。首期不引入 YAML front matter 解析，降低依赖和迁移成本。

### 6.2 索引与检索

- 扫描 `backend/knowledge/*.md`，按 `#`/`##` 标题切分为 chunk。
- 在 SQLite 中保存文档和 chunk，记录 `path`、`title`、`heading`、`content`、`ordinal`、`content_hash`、`updated_at`。
- 首期使用关键词/词元重叠和标题匹配进行召回，取 top N 片段。
- 可选再用 LLM 对召回片段做一次排序和压缩，控制输入 token。
- 回答时返回引用，例如“来源：`capabilities.md` 获客引流客服”。
- 无可靠命中时返回“暂未在知识库中找到对应内容”，并引导用户换一种问法。

### 6.3 知识库变更

- 知识库 Markdown 文件纳入版本管理，修改后由索引器重新生成 chunk。
- 启动时执行增量索引；内容哈希变化才更新，删除文件时同步清理对应 chunk。
- 初期不直接允许微信用户修改知识库；Admin 后续再考虑管理入口。

## 7. 成本与技术可行性分析

`estimate_cost_feasibility` 节点基于知识库 `pricing.md` 和已收集的业务事实生成：

- 成本项：LLM 输入/输出 token、微信客服接入开发、知识库整理、人工接管、运维。
- 量级分档：按日咨询量、平均轮次、平均 token 给出区间估算。
- 技术可行性：渠道、现有系统、数据合规、模型质量、上线时间和运维要求。
- 风险：回复额度、内容准确率、人工接管延迟、客户数据隔离、知识库覆盖率。
- 分阶段建议：PoC 验证闭环 -> 小范围试点 -> 生产化。
- 输出必须标明是 Demo 估算，不代表正式报价。

## 10. 验收标准

- [ ] 普通微信用户首次发消息后，能收到欢迎语和能力菜单。
- [ ] 用户问“你们能做什么”时，能从知识库介绍获客引流、售后客服等能力。
- [ ] 用户问具体知识问题时，回答基于 Markdown 知识库并附来源。
- [ ] 用户表达获客或售后需求时，系统进入多轮业务咨询，能追问行业、渠道、量级和痛点。
- [ ] 用户提供足够信息后，系统能输出成本区间、技术可行性、阶段建议和下一步。
- [ ] 用户要求人工或商务跟进时，系统返回明确 CTA，并在 Admin 后台可识别。
- [ ] 无知识命中或信息不足时，系统不编造，而是澄清或转人工。
- [ ] 现有微信消息幂等、回复配额、footer 和人工接管行为不被破坏。
- [ ] 服务重启后对话状态恢复，不重复回复，不丢新消息。
- [ ] 所有新增后端测试和既有测试通过。

## 11. 暂不纳入首期

- 向量数据库、语义嵌入和复杂 RAG 评估。
- 多租户知识库管理、在线编辑和权限体系。
- 真正的 SCRM、线索自动分发、工单系统或 CRM 对接。
- 自动拨号、支付、合同、签名和正式报价。
- 图片、语音、文件消息的自动处理。
- 多客服账号路由、坐席分组和完整 RBAC。

## 12. 风险与待确认

- 微信客服 5 条回复/48 小时窗口限制会约束多轮业务咨询深度，需要合并提问并及时 CTA。
- 首期关键词检索可能不足以覆盖语义化问题，后续需评估是否引入 embedding。
- LangGraph checkpoint 的 SQLite 表结构与现有 `MessageStore` 应隔离，避免直接复用同一连接造成锁竞争。
- 成本与可行性输出仅用于展示，必须在文案中明确不是正式报价或承诺。
- 业务咨询过程中收集的业务信息需要定义保留范围，避免把潜在客户敏感信息写入普通会话历史。
