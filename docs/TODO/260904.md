# 微信客服用户中心 TODO（2026-09-04）

## 1. 目标

在暂不依赖企业微信“会话内容存档”、已认证服务号网页授权或小程序身份打通的情况下，实现以下闭环：

```text
微信用户发送“我的信息”
  -> 后端识别 external_userid
  -> 获取并缓存微信客服客户资料
  -> 生成一次性登录票据
  -> 客服返回专属 H5 登录链接
  -> 用户登录后查看自己的资料和 AI 客服会话记录
```

第一阶段展示的是本系统通过微信客服 API 收到并保存的消息，不宣称是完整的企业微信“会话内容存档”。

## 2. 身份和数据边界

- `external_userid`：微信客服侧的客户标识，用于关联客服消息。
- 微信昵称、头像：通过 `kf/customer/batchget` 获取，仅用于展示，不是真实姓名或实名凭证。
- `unionid`：只有完成公众号或小程序、微信开放平台以及企业微信的相应绑定后才可能返回。
- 随机登录票据：由本系统生成，不是微信接口返回。
- 内部 `user_id`：作为系统中的稳定用户主键，避免直接使用 `external_userid` 作为业务主键。

- [x] 客户资料获取失败时不阻断 LLM 回复流程。


## 4. 里程碑 B：建立内部用户身份模型

- [x] 创建内部用户表 `app_user`。
- [x] 创建身份映射表 `user_identity`。
- [x] 首次收到新的 `external_userid` 时创建内部用户及身份记录。
- [x] 同一 `external_userid` 的后续消息必须关联同一内部用户。
- [x] 为将来的小程序 OpenID、服务号 OpenID、UnionID 和手机号预留身份类型。
- [ ] 不向前端直接暴露 `external_userid`。

建议模型：

```text
app_user
  id
  created_at
  updated_at

user_identity
  id
  user_id
  provider        # wecom_kf / miniapp / service_account / phone
  subject_id      # open_kfid、appid 或企业主体标识
  external_id     # external_userid、openid 或手机号标识
  unionid nullable
  created_at
```

约束建议：

- [x] `(provider, subject_id, external_id)` 唯一。
- [ ] `unionid` 存在时可用于发现潜在的同一微信用户，但自动合并前需要校验主体和来源。

## 5. 里程碑 C：一次性免密登录票据

- [x] 增加用户指令识别，例如“我的信息”“个人中心”“查看记录”。
- [x] 收到指令后，为当前内部用户生成一次性随机票据。
- [x] 随机值至少具有 128 bit 熵。
- [x] 数据库只保存票据哈希，不保存明文票据。
- [x] 票据有效期设置为 5～10 分钟。
- [x] 票据只能使用一次，消费后记录 `used_at`。
- [x] 同一用户短时间内生成票据需要限流。
- [x] 客服通过文本 URL 或链接消息返回登录地址。
- [x] URL 中不得包含 `external_userid`、昵称、手机号等信息。
- [x] 票据消费成功后创建网站 Session，并立即使票据失效。
- [ ] 登录链接可能被转发；涉及敏感信息时增加手机号验证码等二次验证。

建议的数据表：

```text
login_ticket
  id
  token_hash
  user_id
  expires_at
  used_at nullable
  created_at
  request_ip nullable

web_session
  id
  session_hash
  user_id
  expires_at
  revoked_at nullable
  created_at
  last_seen_at
```

建议接口：

```text
GET  /auth/t/{ticket}             消费一次性票据并建立 Session
POST /auth/logout                 注销当前 Session
GET  /api/me                      获取当前用户资料
GET  /api/me/conversations        获取当前用户的客服会话记录
GET  /api/me/conversations/{id}   获取单个会话详情
POST /api/me/export               申请导出个人数据
DELETE /api/me/data               删除个人数据，需要二次确认
```

## 7. 安全要求

- [ ] 全站只允许 HTTPS。
- [x] Session Cookie 设置 `HttpOnly`、`Secure` 和合适的 `SameSite`。
- [x] 登录成功后轮换 Session ID，防止 Session 固定攻击。
- [x] 所有 `/api/me/**` 查询必须从服务端 Session 获取 `user_id`，禁止信任客户端传入的用户 ID。
- [ ] 对写操作增加 CSRF 防护。
- [ ] 对票据生成、票据消费和个人数据接口增加限流。
- [x] 防止一次性票据重放和并发消费。
- [ ] 敏感操作增加重新验证或二次验证。
- [ ] 不在日志、监控或错误响应中输出票据、Session、Secret、完整 access token 和个人数据。
- [ ] 为资料查看、导出和删除操作增加必要的审计记录。

## 8. 数据与隐私要求

- [ ] 定义客服消息和客户资料的保留期限。
- [x] 区分业务会话记录与企业微信合规“会话内容存档”。
- [ ] 只展示当前登录用户绑定的数据。
- [ ] 不展示系统提示词、LLM 密钥、内部调试信息和其他用户数据。

- [ ] 头像 URL 可能失效，不将其视为永久资源。
- [ ] 在正式对外开放前准备隐私政策和用户协议。

## 12. MVP 验收标准

- [ ] 新客户发送消息后能够获取并缓存昵称和头像。
- [ ] 客户发送“我的信息”后只收到一个短期有效登录链接。
- [ ] 登录票据只能成功消费一次。
- [ ] 用户只能查看自己的资料和客服记录。
- [ ] 转改 URL 参数无法查看其他用户数据。
- [ ] Session 过期后必须重新从客服获取登录链接。
- [ ] 服务重启后票据、Session 和身份映射状态保持正确。
- [ ] 客户资料接口失败时，原有 LLM 客服仍可正常回复。
- [ ] 日志中不包含明文票据、Session、密钥或完整个人信息。
